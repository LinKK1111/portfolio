## Описание
После авторизации на сайте выдаётся кука `token` с ролью пользователя. Задача: повысить привилегии с обычного пользователя до администратора и получить флаг.

## Разведка
- Содержимое куки `token` на первый взгляд выглядело как бессмысленный набор символов.

- Повторяющиеся экранированные подстроки (`\073`) указывали на то, что внутри что-то дополнительно закодировано.
- Через CyberChef: снята экранировка (`Unescape string`), затем рецепт `Magic` определил кодировку — **Base85**.
- После декодирования Base85 получен читаемый JSON: JWT с нестандартным алгоритмом подписи **Lamport**, payload с полем `role: user`, и массив `signature` из 128 строковых ключей.

## Теория: подпись Лампорта
Схема одноразовой подписи на основе хеш-функции:
- Для каждого бита хеша сообщения заранее генерируется пара ключей: один соответствует биту 0, другой — биту 1.
- При подписании для каждого бита сообщения выбирается и раскрывается только один ключ из пары (соответствующий фактическому значению бита).
- Проверяющая сторона сверяет раскрытые ключи с известными открытыми ключами. Если все совпали — подпись верна.
- Для 128-битного хеша нужно 128 пар ключей (256 ключей всего), а подпись раскрывает ровно 128 из них — по одному на бит.

Ключевая уязвимость схемы: **ключи одноразовые**. Если подписать два разных сообщения одной и той же парой ключей, для любого бита, где значения в сообщениях отличаются, атакующий получает **оба** ключа пары — и может подделать подпись для произвольного значения этого бита.

## Эксплуатация

### Шаг 1. Определение хеш-функции
Перебором алгоритмов подобрана хеш-функция, по длине соответствующая 128 ключам — **MD5** (128-битный хеш). Хеш payload'а переведён в биты: это и есть последовательность, которой соответствует раскрытая часть подписи.

После этого для каждого бита известен один из двух ключей пары:
```
bit[0] = {key_1, "A0|6gP;>cye|3CH@1nnh"}   # key_1 неизвестен
bit[1] = {"Ps6NAQIi#0ee1w?6GTwU", key_4}   # key_4 неизвестен
...
```

### Шаг 2. Сбор недостающих ключей
Поскольку сервер переиспользует одну и ту же пару ключей для подписи (нарушение правила одноразовости Lamport), можно раскрыть вторую половину каждой пары:
- Зарегистрирован второй аккаунт с другим `username` → новый хеш payload'а → новый набор раскрытых битов подписи.
- Для битов, значение которых отличается от первого аккаунта, раскрывается второй, ранее неизвестный ключ пары.
- Процесс повторён для нескольких аккаунтов (автоматизировано скриптом на Python), пока для всех 128 бит не был собран **полный комплект пар ключей**. Один из битов (№3) не менялся достаточно долго — потребовалась регистрация 13 аккаунтов, чтобы получить нужное значение.

### Шаг 3. Подделка подписи для нужного payload'а
- Собран целевой payload: `{"user_id":1,"username":"ever","role":"admin"}`, посчитан его MD5-хеш и переведён в 128 бит.
- Для каждого бита: если значение совпадает с battle-тестовым (уже подписанным) сообщением — переиспользован тот же раскрытый ключ; если отличается — подставлен второй, добытый на шаге 2 ключ.
- Таким образом собрана **корректная подпись** для payload'а с ролью `admin`, хотя сервер его никогда не подписывал.

## Результат
Флаг получен через полную подделку подписи Lamport для произвольного payload'а, без знания закрытых ключей сервера напрямую — только за счёт повторного использования одноразовой схемы подписи.

## Взгляд защитника
- **Главная причина — архитектурная ошибка:** схема Лампорта по определению одноразовая (OTS, one-time signature). Повторное использование одной пары ключей для подписи разных сообщений полностью ломает её безопасность. Для многократной подписи нужны либо деревья Меркла поверх OTS (как в XMSS/LMS), либо обычная асимметричная схема (RSA, ECDSA, EdDSA), рассчитанная на многократное использование одного ключа.
- **Прозрачность формата токена:** содержимое подписи и payload были доступны клиенту в декодируемом виде (Base85 — не шифрование, а просто кодирование). Секретные или чувствительные к повторному использованию компоненты не должны передаваться клиенту в любом виде, даже закодированном.
- **Отсутствие ограничений на регистрацию:** возможность свободно и массово регистрировать новые аккаунты позволила собрать произвольное количество подписанных сообщений с предсказуемой структурой (меняется только `username`). Рейт-лимит и обязательная верификация (капча, подтверждение email) замедлили бы атаку на порядки.
- **Детектирование:** множественная регистрация новых аккаунтов с одного IP или User-Agent за короткий промежуток времени — аномалия, которую стоит детектировать (счётчик регистраций на IP/сессию в единицу времени). Также подозрителен паттерн: один и тот же пользователь получает несколько разных JWT с одинаковой структурой payload, но где меняется только одно поле между отличающимися по хешу сообщениями, — это способ собрать материал для атаки на одноразовую подпись.
