## Описание
Дано: веб-сайт и архив с исходным кодом. Задача: получить хеш пароля администратора сервиса.

## Разведка
- В интерфейсе сервиса обнаружена фича привязки Telegram-аккаунта.

- В исходном коде найден метод `is_user_exists`, где значение попадает в SQL-запрос как обычная строка — потенциальная SQL-инъекция.
<img width="2178" height="276" alt="изображение" src="https://github.com/user-attachments/assets/0be28ff7-f8f8-4804-94df-db83f8deb68e" />

- В скриптах инициализации найдено, что при разворачивании проекта создаётся учётка `admin`, хеш пароля которой хранится в таблице `users`, поле `password_hash`.

- Метод `is_user_exists`, уязвимый к инъекции, доступен только из эндпоинтов, требующих прав администратора. Вывод: нужно либо повысить привилегии, либо захватить аккаунт админа.

## Эксплуатация

### Шаг 1. Захват аккаунта администратора (атака на привязку Telegram)
Механизм привязки:
1. `POST /send_tg_link` с `username` → сервер генерирует токен `create_signin_token_for_user`, кладёт в кэш на 5 минут (`TTLCache(maxsize=16384, ttl=60*5)`).
2. Токен — `secure_uuid(username)`, зависящий от MAC-адреса сервера и текущего времени с точностью 0.1 секунды.

Проблемы и решения:
- **MAC-адрес неизвестен.** Привязал свой аккаунт, получил сгенерированную сервером ссылку, декодировал hex → восстановил параметры MAC_HEX_P1/P2, подставил их в переписанный локально метод генерации токена.
- **Сервер не знает о локально сгенерированной ссылке**, пока сам её не создаст и не положит в кэш.
- **Токен зависит от времени с точностью 0.1 сек.** Предугадать момент генерации на сервере нереально, поэтому запущен скрипт в 2 потока: один каждые 100 мс генерирует токен для `admin`, второй в параллели шлёт `POST /send_tg_link` с `username=admin`. За 2 секунды локально генерируется ~20 токенов, один из них с вероятностью 100% совпадает с серверным.
- Перебор сгенерированных ссылок авторизации дал рабочую — вход в аккаунт администратора выполнен.

### Шаг 2. Blind SQL Injection
В админке доступен просмотр заметок пользователей по адресу `/admin/users/{username}/notes`, где `{username}` подставляется в запрос `SELECT EXISTS(...)` без экранирования.

- Проверка инъекции: `ever') AND 141=141 AND ('m'='m` → запрос возвращает 1 (HTTP 200), подтверждая SQLi.
- Логика побитового/посимвольного извлечения: ответ 200 = условие истинно, 302 = ложно.
- Сначала определена длина хеша (`LENGTH(password_hash) > 32` и т.д.) — 64 символа.
- Затем посимвольным перебором по алфавиту `0123456789abcdef` через конструкцию
  `SUBSTRING(password_hash FROM N FOR 1) = 'X'`
  восстановлен весь хеш, автоматизировано скриптом (перебор символа для каждой позиции, фиксация при статусе 200).

## Результат
Получен полный хеш пароля администратора (`password_hash`, 64 символа), что и было флагом задачи.

## Взгляд защитника
- **Race condition в генерации токена:** токен привязки не должен зависеть от предсказуемых параметров (MAC-адрес + время с точностью 0.1с). Использовать криптографически случайный токен (`secrets.token_urlsafe`), непредсказуемый и не воспроизводимый атакующим.
- **Отсутствие биндинга токена к устройству/сессии:** токен для привязки Telegram должен быть одноразовым и проверяться с учётом источника запроса.
- **SQL-инъекция:** использовать параметризованные запросы / ORM вместо подстановки строк, валидировать входные данные.
- **Детектирование:** в логах веб-сервера такая атака оставляет характерный след — серию запросов к одному и тому же эндпоинту с разными payload'ами и чередованием кодов 200/302 за короткий промежуток времени. Правило детектирования: много запросов от одного IP к `/admin/users/*/notes` с нетипичными символами в пути (кавычки, SQL-ключевые слова) за короткий интервал.
