## Описание
Веб-сервис с авторизацией, вход доступен под `guest:guest`. Флаг виден только пользователю с ролью admin.

## Разведка
- В куках найден JWT, определяющий роль пользователя.
- Декодирование токена показало алгоритм подписи `HS256` и поле роли в payload.

## Эксплуатация
- Прямая замена `guest` на `admin` в payload не сработала: подпись токена зависит от всего содержимого, и изменение payload делает подпись невалидной без знания секретного ключа.
- Секрет подобран офлайн-брутфорсом через `hashcat` по словарю — найден секрет `IC3QU33NS`.
- Зная секрет, сформирован новый токен с ролью `admin` и валидной подписью (`eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...`).
- Токен подставлен вместо старого в куки — получен доступ к флагу.

## Результат
Получен флаг, доступный только пользователю с ролью admin.

## Взгляд защитника
- **Слабый секрет HS256** — главная причина компрометации. Секрет должен быть длинным, случайным и регулярно ротируемым, либо стоит перейти на асимметричные алгоритмы (RS256/ES256), где секрет подписи не нужно раздавать клиенту косвенно.
- **Роль не должна определяться только клиентским токеном** без дополнительной проверки на сервере (например, сверка с базой при критичных действиях).
- **Детектирование:** большое количество неудачных попыток авторизации с переданными JWT, различающимися только подписью при одинаковом payload, — признак офлайн-брутфорса секрета, обнаруженного постфактум по логам (если токен логируется) или по резкому всплеску запросов с валидной структурой, но разной подписью.
